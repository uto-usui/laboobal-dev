# 生成した 3D をデザイン画に近づける方法

2026-11-18 に Codex に調べさせた結果です（依頼文は `scripts/toy-character/prompt-fidelity-research.md`）。この手順で作ります。数値は制作の基準として決めたもので、公式の保証値ではありません。

このキャラクターでは、既存の体を残し、頭だけを大きな切り抜きから別生成し、原画の輪郭・顔の位置へ合わせてから、色を投影し直す手順を採用します。眼球・まぶた・眼鏡は予定どおり別に作ります。リュックと指は、画像生成の設定変更で直そうとせず、後工程で形を作り直します。

頭の別生成はAssetFurnaceに「Hero face」として実装されています。ただし、このキャラクターで改善することは未確認です。以下は、既存実装と公式資料から決めた制作手順であり、成功を実測した報告ではありません。ファイルは変更していません。

1. 比較の基準と座標を先に固定する

正面の形・顔・配色は`v4.png`を正とします。眼鏡なし画像は生成用、横・背面図は正面から分からない形と柄の参考にします。

先に直すべきなのは、比較の尺度です。

- `scripts/toy-character/img3d-render.py`は全身を高さ1に正規化しています。
- `scripts/toy-character/generated_mesh.py`は位置だけを直し、全高約0.888644のまま扱っています。今回、GLBの座標範囲からも確認しました。
- `face.py`の7〜11mmという差や補正量を、全高1mの比較へそのまま持ち込むことはできません。

制作コピーを全高1m、靴底Z=0、正面−Yに統一します。原画との比較は、既存の基準である頭頂y=36、靴底y=1213、全高1177pxを使います。正投影を仮定すると、原画の座標は次の初期値に変換できます。

```text
X = (画像のx − 627) / 1177
Z = (1213 − 画像のy) / 1177
```

奥行きYは正面画だけでは決まりません。横図を補助に使い、判断できない部分は生成形状を保ちます。顔の位置を測る前に、頭の大きさ・向き・画角を合わせます。

色の評価画像は、照明なしの色表示と通常の照明付き表示を分けます。既存の比較はAgXと照明を通しているため、見える色差すべてを生成テクスチャの誤りとは扱えません。AgXには明るい色を脱彩する処理があります。[Blenderの色管理](https://docs.blender.org/manual/ko/5.2/render/color_management/displays_views.html)

2. 頭の入力を、原画を描き変えずに作る

眼鏡なし画像から、髪・耳・顔・短い首を切り出します。開始領域は既存`review_images.py`と同じ`(397, 10, 857, 470)`とし、その中の服・肩ひも・背景をアルファで除きます。髪先、耳、顎は切りません。

PillowのLANCZOSで1024px四方へ整えます。Real-ESRGANなどによる顔の描き足しは使いません。拡大の目的は、頭へ生成の空間解像度を割り当てることです。原画にない細部を復元できるわけではありません。

入力について、公式実装と手元の移植から確認できた条件は次のとおりです。

| 項目 | 確認結果と今回の扱い |
|---|---|
| 解像度 | 公式Pixal3Dの前処理は、まず入力の長辺を最大1024へ縮小します。1254pxをさらに大きくして渡す効果は限定的です |
| 余白・被写体の大きさ | アルファの外接矩形を取り、その長辺の1.1倍の正方形へ切り直します。被写体は長辺の約91%。自前の大きな余白は内部で取り除かれます |
| 背景 | 検査済みRGBAを渡します。単にアルファチャンネルが存在するだけでは不十分です |
| 正面性 | 正面画像は必須条件ではありません。学習用レンダは複数方向を使います。今回は正面デザインを優先するため、正面を主入力にします |
| 光と影 | 今の柔らかい陰影を生成入力には残します。強い影や床の落ち影はマスクへ入れません。「完全な無影画像が公式必須条件」という根拠は確認できませんでした |
| 細い部品 | 眼鏡は外して生成し、Blenderで作ります。今回の眼鏡付き生成では太いフレームと不透明なレンズ相当になっており、別部品の方が形・透明度・可動を管理できます |

前処理の根拠は、公式`pixal3d_image_to_3d.py`と手元の`vendor/pixal3d-cpp/src/image_preprocess.cpp`です。公式論文も、切り抜き境界のノイズが形状の乱れへ増幅されることを制約として挙げています。[公式前処理](https://github.com/TencentARC/Pixal3D/blob/master/pixal3d/pipelines/pixal3d_image_to_3d.py)、[学習用カメラ・解像度](https://github.com/TencentARC/Pixal3D/blob/master/data_toolkit/render_cond.py)、[論文の制約](https://arxiv.org/html/2605.10922v1#S4.SS5)

既存の背景除去画像では、アルファの外接矩形を今回読み取り確認しました。眼鏡なし全身は`(289, 36, 957, 1215)`です。背景除去後は、髪・指先・靴の欠損と、床の影が残っていないかを画像で検査します。頭の切り抜きにも同じ検査を行います。

3. 頭を固定条件・4つのseedで生成し、形で選ぶ

設定は、手元で動いた条件を基準に固定します。

| 設定 | 採用値 | 理由 |
|---|---:|---|
| `res` | 1024 | 手元の単画像ラッパーと`--sv-image`は1024のみ対応 |
| `steps` | 12 | 現行の生成と同条件。8は移植側の高速化設定で、忠実さを優先する今回は使わない |
| `gss` | 10 | 現行条件を維持。移植側には細い部品の欠落を減らした記録がある |
| `gsh` | 7.5 | 手元のランタイム既定値を明示 |
| `fov` | 0.3490658503988659 | 20°の仮想カメラ。原画の実際のFOVだとは断定しない |
| `seed` | 42、43、44、45 | 設定探索をせず、確率的な生成差だけを比較する |

制作時の生成コマンドは次です。`head-front-rgba.png`は手順2で作る新しい入力で、現時点では未作成です。

```sh
source .work/toy-character/img3d/env.sh
TOY_AF="$IMG3D_ROOT/AssetFurnace"

for toy_seed in 42 43 44 45; do
  python "$TOY_AF/scripts/pixal3d_generate.py" \
    "$IMG3D_ROOT/fidelity/input/head-front-rgba.png" \
    "$IMG3D_ROOT/fidelity/head-s${toy_seed}.glb" \
    --res 1024 \
    --steps 12 \
    --gss 10 \
    --gsh 7.5 \
    --fov 0.3490658503988659 \
    --seed "$toy_seed" \
    --no-matte
done
```

`--no-matte`は、検査済みのアルファを再処理させないためです。背景付き画像で使う設定ではありません。

stepsは各生成段階の数値積分回数、gssは粗い占有形状への画像条件の強さ、gshは詳細形状への条件の強さです。増やせば顔の位置が正しくなる、という対応はありません。特に「gssを上げるほど忠実」という根拠はなく、手元のラッパーにも13で細い部品が分離した記録があります。公式配布設定は12 steps、形状側のguidance 7.5を使っています。[公式設定](https://huggingface.co/TencentARC/Pixal3D/blob/main/pipeline.json)

複数seedから選ぶこと自体は確率的生成に対する妥当な方法ですが、「4本が最適」という公式推奨はありません。4本は今回の制作予算です。穴・二重の耳・髪の欠損を先に除外し、後述の輪郭と顔の位置で順位を付けます。肌の色やハイライトの好みで選びません。

なお、公式の現在の実装はTRELLIS.2ベースで、論文版はDirect3D-S2ベースです。論文の比較成績を、そのままMac移植の成績とは扱えません。[公式の版の説明](https://github.com/TencentARC/Pixal3D#-branches)

4. 頭を原画へ合わせ、残差だけを制約付きで直す

頭の別生成は、既存`image_to_3dlab/hero.py`にも実装されています。今回はその考え方を使い、一括実行の`hero_route.py`は採用しません。

一括処理には、今回の工程と合わない点があります。

- 最初に体を減面します。
- 頭の拡大にReal-ESRGANを使います。
- 新しい頭を古い頭の寸法・形へ位置合わせします。
- 古い後頭部を縮めて内側へ残す処理があります。
- `hero_blender.py`の結合はオブジェクトのJoinで、首の頂点を接続する処理ではありません。

今回は、原画から測った頭頂〜顎の高さと顔幅で等方スケールを合わせ、原画の顎・耳・顔の中心へ配置します。頭頂〜顎354pxという既存の基準なら、全高1mに対する初期高さは約0.301mです。生成された首や台座を含むGLB全体の高さで合わせません。[既存の頭別生成処理](https://github.com/Bingeljell/image-to-3dlab/blob/919830b7294b9531da64817452db9cf9a48d0b71/scripts/hero_route.py)、[配置・差し替えの実装](https://github.com/Bingeljell/image-to-3dlab/blob/919830b7294b9531da64817452db9cf9a48d0b71/image_to_3dlab/hero.py)

小さい残差には、次の方法を使います。

- Blenderで2,000〜5,000頂点程度の制御用メッシュを作る。
- 顎・頬の輪郭、鼻翼・鼻先、口角・唇の中央を原画の対応点へ合わせる。
- 首、後頭部、動かしたくない髪際を固定する。
- Laplacian Deformで周囲の形を保ちながら変形し、高密度面へ変形を移す。
- 奥行きは横図を弱い制約として使い、正面だけを合わせて平らにしない。

これは「鼻を何mm押すか」を繰り返す方法より、目標と変形範囲を明確にできます。ただし、形を保つ変形法なので、大きく違う鼻や唇を自動で正しい形へ作り直すものではありません。大きな残差は不合格として残します。高密度面へ直接かけず制御用メッシュを使うのは、計算を軽くし、固定点を管理するためです。[BlenderのLaplacian Deform](https://docs.blender.org/manual/ru/5.2/modeling/modifiers/deform/laplacian_deform.html)、[制約付き形状変形の原理](https://igl.ethz.ch/projects/ARAP/)

今回の押し引きが失敗した理由は、コードからも説明できます。`face.py`は、領域ごとの変位を重ね、眼窩を球の受け皿へ移しています。原画の輪郭への誤差や面の潰れを最小化する処理ではありません。記録上、最大変位は眼窩で約66.8mmあり、顔中央の約10mmの持ち上げだけではありません。また、UVと元画像を保っているため、形を変えても鼻孔・唇・顎周辺に描かれた陰影は残ります。法線の再計算だけでは消えません。

5. 首・リュック・指と、別部品の目を作る

首は襟に隠れる位置で接続し、既存`mesh-method.md`の仕様に合わせて周方向32頂点、長さ方向6リングを初期値にします。頭側と体側の境界を対応させて面でつなぎ、法線とウェイトも連続させます。全身Voxel Remeshで一体化する方法は使いません。[Blenderの境界ループ接続](https://docs.blender.org/manual/en/5.2/modeling/meshes/editing/edge/bridge_edge_loops.html)

リュックは、比較画像を見る限り色だけでなく形も原画と違います。既存のリュック領域を分離し、背面図の外形と横図の厚みから低密度の形を定義します。ポケットと持ち手も形として作ります。赤い生成面へ柄を投影するだけでは、原画のリュックにはなりません。

指の根元の癒着は、stepsやテクスチャで解消する問題ではありません。予定している手の作り直しで、指間と関節リングを作ります。

眼球・まぶたは、原画で測った開口部と虹彩の大きさを目標にします。球の半径から見える目の大きさを決めません。生成された目の底を開口し、肌へ描かれた白目・瞳・ハイライトを除きます。眼鏡の影も肌へ残しません。

6. 投影前に、色と照明を分ける

原画の画素をそのまま貼れば正面の見た目は近づきますが、鼻下・顎下・髪の影も貼り付きます。three.jsで照明を動かすなら、ベースカラーには照明を取り除いた色が必要です。

今回は、Marigold IID Appearanceを補助に使ってアルベド、つまり照明を除いた表面色を推定します。

```text
モデル: prs-eth/marigold-iid-appearance-v1-1
実行: Diffusers / MPS
型: float32
processing_resolution: 768
num_inference_steps: 4
ensemble_size: 3
seed: 0
match_input_resolution: True
```

公式モデルカードは実効解像度を約768pxと説明し、DiffusersはMPS経路を案内しています。ただし、今回のアニメ調の顔で正しい色を出すかは未確認です。[モデルカード](https://huggingface.co/prs-eth/marigold-iid-appearance-v1-1)、[公式の利用方法](https://huggingface.co/docs/diffusers/v0.43.0/api/pipelines/marigold)

推定結果は無条件に採用しません。肌・服・髪を別マスクで扱い、原画の中間調を基準に色を合わせます。頬の赤み・唇・動物柄は残し、鼻孔の黒さや髪の落ち影を表面色として残さないようにします。顔の推定が崩れた箇所は、原画から採った肌色と頬・唇のマスクで塗ります。

StableDelightは鏡面反射の除去が目的で、顎下などの拡散陰影をすべて除く道具ではないため、今回は選びません。[StableDelight公式](https://github.com/Stable-X/StableDelight)

Emissionベイクは照明を追加せず色を転写できますが、画像に描かれた影を消す機能ではありません。[Blenderのベイク仕様](https://docs.blender.org/manual/en/latest/render/cycles/baking.html?highlight=bake)

7. 形と目の開口を確定してから、最終UVへ投影する

正面は原画、背面は背面図から投影します。横図は腕のポーズが違うため、頭・リュックなど対応が取れる部位だけに使います。服の正面は眼鏡なし編集画像ではなく`v4.png`から採り、編集時に生じた小さな色変化を持ち込みません。

投影は、次の条件付きで行います。

| 条件 | 今回の設定 |
|---|---|
| 可視性 | カメラから最初に見える面だけに投影する。髪越しに肌へ投影しない |
| 面の向き | 面法線とカメラ方向の内積が0.35以下では不使用、0.75以上で全面採用、その間を滑らかに混ぜる |
| 部位 | 肌・髪・左右袖・ひも・リュックを別マスクにする |
| 境界 | 切り抜き端・遮蔽境界は入力1024px換算で約8pxを混合帯にする |
| 複数画像 | 柄や顔は1枚を優先。食い違う顔・柄を平均して二重にしない |
| 横への伸び | 正面から見えにくい頬・耳・鼻側面へ正面画素を引き伸ばさない。横画像か、同部位の色で補う |
| 未観測面 | 頭頂、顎裏、脇などは生成色を基礎に同部位の色へ合わせ、未観測として記録する |

手元の`photo_paint.py`には、可視性・面の向き・境界の減衰・複数画像の混合が実装済みです。ただし、既定の`view_align.py`は画像の特徴を生成メッシュ側へ少し動かします。今回は原画を目標にするため、形を合わせた後の最終投影ではこの自動位置補正を使いません。

既存投影の確認には、次のコマンドを使えます。

```sh
python "$TOY_AF/scripts/photo_paint.py" \
  "$IMG3D_ROOT/out/v4-noglasses.glb" \
  "$IMG3D_ROOT/out/v4-noglasses.svviews" \
  "$IMG3D_ROOT/fidelity/body-projection-check.glb" \
  --no-align \
  --facing-low 0.35 \
  --facing-high 0.75 \
  --weights "$IMG3D_ROOT/fidelity/body-projection-weights.png"
```

これは元座標・単一メッシュに対する確認用です。頭の配置、首の接続、新UVを行った最終モデルには、カメラも同じ変換を適用したBlender用の投影処理が必要です。その処理と部位マスクは未実装です。

BlenderのUV Projectは投影座標を作れますが、それだけで遮蔽判定や画像間の継ぎ目は解決しません。通常のアトラスUVを維持し、上の条件で得た色をそこへ焼きます。[UV Project](https://docs.blender.org/manual/id/5.2/modeling/modifiers/modify/uv_project.html)、[投影による伸びの説明](https://docs.blender.org/manual/fi/5.2/modeling/meshes/editing/uv.html)

以降の減面・新UV・法線ベイク・リグは`docs/toy-character/mesh-method.md`につなぎます。ただし、法線の焼き元も今回確定した形へ更新します。古い鼻や唇の凹凸を、新しい顔へ焼き戻さないことが必要です。

「近い」の判定は、次の数値と画像で行います。数値は公式の保証値ではなく、今回の制作基準です。

| 検査 | 基準 |
|---|---|
| 目・鼻・口の位置 | 原画1254px座標へ戻して、各対応点の誤差2px以内を目標。全高1m換算で約1.7mm |
| 目の大きさ | 左右それぞれ、開口部の幅・高さ、虹彩径、目の中心間隔が原画の±5%以内 |
| 鼻・口の大きさ | 鼻翼幅、鼻の縦幅、口幅、唇の厚みが原画の±8%以内 |
| 頭の輪郭 | 正面の髪込みシルエットIoU 0.97以上、輪郭距離P95が原画上3px以内を目標 |
| 顔の輪郭 | 顎・頬・こめかみを髪と分けて比較し、局所的な膨らみがない |
| 色 | 同一の表面色を表す対応領域でCIEDE2000の中央値3以下、P95が6以下を目標。肌・左右袖・髪・リュックを別集計 |
| 継ぎ目 | 首・耳・髪際・袖・リュックで、投影線や異なる部位の色混入がない |
| 立体としての破綻 | 正面、左右45°、左右側面、背面で二重の耳・唇、髪の穴、顔の平板化がない |
| 再照明 | 大きなライトを左右へ動かし、鼻・顎・眼鏡の影が固定されたまま残らない |
| 可動 | 首を左右30°・上下20°へ動かして裂けない。まばたきで余分な白目が露出しない |

対応点は、このキャラクターの画像へ一度注釈して固定します。人間の実写顔向け検出器の値を、そのままアニメ顔の正解にはしません。色差も、陰影付き原画とアルベドを直接比較せず、投影に使った表面色同士で測ります。最終の照明付き画像は原画と並べて別に判定します。

seedの選択は、破綻を除外した後、輪郭誤差、鼻・口の位置と大きさ、斜めからの形の順に行います。4本とも基準を満たさなければ、別生成した頭を採用済みとは扱いません。

多視点入力については、経路があることをコードで確認できました。

| 経路 | 確認結果 |
|---|---|
| AssetFurnaceのラッパー | `pixal3d_generate.py front.png out.glb --back back.png`に対応 |
| 移植の下位CLI | `trellis-cli --views DIR --pixal3d-weights mv --models DIR ...`で任意の視点列を読める |
| 必要な情報 | 各画像、4×4のcamera-to-world行列、水平FOVのラジアン値、`mesh_scale` |
| カメラ規約 | 世界はZ-up、カメラはローカル−Zを見る。最初の画像が基準の正面 |
| 手元の導入状況 | 単画像用重みは存在。多視点用重みの導入は未確認で、確認したモデル置き場には単画像用だけがありました |

公式の多視点実装は2026年9月公開済みです。画像の構図はカメラ記述と一致する必要があります。[公式の入力形式](https://github.com/TencentARC/Pixal3D#multi-view-inference)、[公式多視点コード](https://github.com/TencentARC/Pixal3D/blob/master/inference_mv.py)

手元の簡易経路は、正面・背面をそれぞれ768px、被写体90%へ整え、20°・距離約2.83564の対向カメラを作ります。また、`--back`経路では`--fov`がカメラ生成へ渡らず、固定20°になります。多視点のFOV調整にこの引数を使ってはいけません。根拠は`pixal3d_generate.py`の`write_front_back_views()`と`_rig()`です。

今回は多視点による全身再生成を採りません。横図の腕は下がっており、正面・背面とはポーズが違います。さらに、3枚を個別に中央へ切り抜くだけでは、同じカメラ中心・尺度の図にはなりません。矛盾した画素特徴を融合しても、正面を優先してくれる保証はありません。原画を変形して整合させるより、今回は部位を限定した形合わせと投影に使います。

ほかの方法を選ばなかった理由は次のとおりです。

| 方法 | 判断 |
|---|---|
| 全身のsteps・gssを順番に増やす | 顔へ割り当たる解像度や、未観測の背中の情報を増やせないため採らない |
| 単画像を1536で再生成 | 公式Python版にはあるが、手元の単画像経路は1024限定。解像度変更だけで顔の比率が直る根拠もない |
| Hero faceの一括実行 | 先行減面、生成拡大、古い頭への位置合わせ、内部メッシュの重ね合わせが今回の工程と合わない |
| 正面画を全面へ貼る | 横へ伸び、鼻孔・顎下・眼鏡の影も固定される |
| 数値の局所変位を追加する | 原画への対応点・輪郭・形の連続性を目標にしていないため、同じ問題を繰り返す |
| 全顔の平滑化・Voxel Remesh | 鼻だけでなく髪際・耳・唇など、残したい形まで変える |

2026-11-18時点で、無料・Macローカル・人物のデザイン忠実度という条件を満たし、Pixal3Dより明らかに優れると確認できた乗り換え先はありません。

- TRELLIS.2はMac移植がありますが、このキャラクターの顔で優れるという一次資料は確認できませんでした。公式版の動作条件はLinux・NVIDIAです。[TRELLIS.2公式](https://github.com/microsoft/TRELLIS.2)
- Hunyuan3DにはShape/PaintのSwift・MLX移植があります。ただし、この顔の位置・比率の再現で優れる証拠はありません。[移植元の実装](https://github.com/ZimengXiong/Hunyuan3D-Swift)
- Step1X-3Dは公式ではCUDAを使います。Apple Siliconで動く非公式実装も確認できたため「Macでは動かない」とは言えませんが、その経路は形状のみで実験扱いです。[公式](https://github.com/stepfun-ai/Step1X-3D)、[Mac対応を実装したプロジェクト](https://github.com/lpalbou/abstract3d/blob/main/docs/models.md)
- Hunyuan3D 3.0／3.1は公式クラウドAPIで確認できましたが、Macへ入れられる公開重みは未確認です。[公式API](https://www.tencentcloud.com/document/api/1284/75540)

- 正面の`v4.png`を最優先とし、ほぼ正投影として形を合わせます。原画の実際のカメラ・照明は未確認です。
